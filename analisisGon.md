###Análisis de Viabilidad y Arquitectura para la Migración de Rizoma a Entornos Móviles a través de la Red Tor

#Resumen Ejecutivo
El presente documento analiza la viabilidad técnica de portar "Rizoma", una aplicación de mensajería P2P basada en la red Tor y escrita en Go, a sistemas operativos móviles (iOS y Android). A partir del análisis del código fuente proporcionado, se establece que la migración es completamente viable, aunque requiere una reestructuración arquitectónica sustancial. Se descarta la ejecución directa de binarios de escritorio (como .exe) en favor de librerías nativas de Tor, y se propone una separación estricta entre la lógica de negocio en Go y una nueva interfaz gráfica adaptada a dispositivos táctiles.

1. Análisis del Estado del Arte: Alternativas P2P sobre Tor en MóvilesPara establecer un marco de referencia sólido, es imperativo analizar cómo aplicaciones existentes han resuelto la comunicación P2P anónima en dispositivos móviles.
- Briar: Es un cliente de mensajería diseñado exclusivamente para Android (y recientemente con versiones de escritorio en desarrollo) que no depende de servidores centrales. Briar enruta todo su tráfico a través de la red Tor mediante la integración nativa del demonio de Tor como un servicio en segundo plano dentro de Android. Además, implementa mecanismos de respaldo para sincronizar mensajes vía Bluetooth o redes Wi-Fi locales cuando no hay acceso a Internet. Su arquitectura demuestra cómo gestionar el alto consumo de batería que implica mantener una conexión continua a Tor en un dispositivo móvil.
- Cwtch: Es el referente más directo para la migración de Rizoma, ya que comparte una pila tecnológica casi idéntica. Cwtch utiliza Tor V3 Hidden Services para conexiones P2P, mantiene toda su lógica criptográfica y de red escrita en Go, y emplea interfaces de usuario separadas (actualmente en Flutter para abarcar múltiples plataformas). Cwtch valida empíricamente que es posible empaquetar una aplicación Go que interactúe con Tor y publicarla en entornos móviles mediante el uso de librerías vinculantes.
- Session: Aunque utiliza la red de enrutamiento Lokinet (un fork conceptual de conceptos similares a Tor) en lugar de la red Tor tradicional, Session demuestra cómo una interfaz de usuario fluida y moderna en sistemas móviles puede ocultar la complejidad criptográfica del enrutamiento cebolla, brindando una experiencia equiparable a aplicaciones de mensajería convencionales.

2. Diagnóstico de la Arquitectura Actual de RizomaEl análisis del código fuente de Rizoma revela una aplicación monolítica orientada a escritorio con un fuerte acoplamiento a las capacidades de los sistemas operativos tradicionales.

 2.1. Gestión de la Red TorActualmente, el archivo network.go utiliza el paquete [github.com/cretz/bine/tor](https://github.com/cretz/bine/tor) para iniciar y gestionar el proceso de Tor. El método StartTor busca activamente un archivo ejecutable tor.exe en el sistema de archivos local para ejecutarlo como un subproceso.
Problema: Los sistemas operativos móviles operan bajo arquitecturas ARM (no x86/x64) y utilizan entornos de ejecución encapsulados (sandboxing) que prohíben estrictamente la ejecución de binarios arbitrarios ajenos a la aplicación. Un archivo .exe es incompatible física y normativamente con Android e iOS.  

 2.2. Lógica Criptográfica y de TransferenciaLos módulos crypto_utils.go y file_transfer.go contienen implementaciones de cifrado AES-GCM, derivación de llaves SHA-256 y fragmentación de archivos en bloques de 32KB. Esta lógica es puramente matemática e independiente del sistema operativo.
Ventaja: Esta sección del código es altamente portable.  

 2.3. Interfaz de Usuario (TUI)La interfaz actual está implementada utilizando el framework Bubble Tea, como se evidencia en ui.go, diseñando vistas de terminal matriciales que capturan eventos de teclado convencionales (como tea.KeyEnter o tea.KeyEsc).
Problema: Las interfaces de terminal (TUI) asumen la existencia de un teclado físico constante y la capacidad de procesar eventos de entrada por consola, elementos inexistentes o poco prácticos en pantallas táctiles donde los teclados virtuales obstruyen el 50% de la pantalla.  

3. Estrategia de Migración y Arquitectura PropuestaCon base en el análisis previo, se propone la siguiente arquitectura para optimizar la migración de Rizoma, garantizando las mejores prácticas de desarrollo móvil.

 3.1. Solución para el Demonio de Tor en MóvilNo se debe intentar portar ni compilar el ejecutable de Tor directamente desde Go. La mejor manera de abordar este requerimiento es delegar la ejecución de Tor al sistema operativo nativo del dispositivo y configurar la aplicación Go para conectarse a él.
  -Android: Se recomienda integrar la librería Tor-Android (mantenida por The Guardian Project). Esta librería levanta un servicio local que expone un puerto SOCKS5.
 - iOS: Se debe utilizar Tor.framework, un envoltorio en C/Objective-C que permite instanciar el proxy de Tor directamente desde el código nativo de Apple.
- Adaptación en Rizoma: Se debe modificar network.go para eliminar la dependencia de bine/tor y de tor.exe. En su lugar, el NetworkManager de Rizoma simplemente recibirá como parámetro de configuración el puerto local (ej. 127.0.0.1:9050) que el sistema móvil haya habilitado tras inicializar Tor nativamente.  

 3.2. Portabilidad de la Lógica en Go (gomobile)Para reutilizar el código escrito en Go en plataformas móviles, se debe emplear la herramienta oficial del ecosistema Go denominada gomobile bind.
 - Lo que se puede reusar: Los archivos crypto_utils.go (derivación de llaves y cifrado), file_transfer.go (lógica de fragmentación de archivos) y config.go (estructuras de configuración) se pueden compilar directamente. Se mantendrá intacta la lógica matemática. 
 - Lo que se debe reescribir: Además de la eliminación del invocador de tor.exe en network.go, se deben abstraer las llamadas al sistema de archivos locales. Por ejemplo, las referencias directas a directorios estáticos como "loadingbay_in" y "loadingbay_out" en file_transfer.go deben ser reescritas para aceptar rutas inyectadas dinámicamente. Los sistemas móviles restringen la escritura a directorios de caché de la aplicación, por lo que el frontend (Kotlin/Swift) deberá dictar dónde tiene permiso Go para leer y escribir archivos.  
  3.3. Adaptación de la Interfaz Gráfica TUITrasladar un grid monoespaciado de ASCII a móvil de forma literal (mediante emuladores de terminal embebidos) resulta en una deficiencia severa de usabilidad, también conocida como un antipatrón de diseño móvil.La arquitectura recomendada: Desacoplar por completo la vista de la lógica. Se debe descartar por completo la capa de presentación actual (ui.go, ui_components.go, ui_assets.go). En su lugar, se sugiere reconstruir el frontend utilizando un framework móvil moderno como Flutter o React Native.  Para conservar la identidad visual de Rizoma:
  - Estilización Nativa: Configurar el framework móvil para utilizar fuentes monoespaciadas puras (ej. JetBrains Mono o Fira Code).
  - Paleta de Colores: Mantener los fondos negros y utilizar los códigos hexagonales correspondientes a los colores ANSI utilizados actualmente en config.go y la TUI (como el rosa ANSI "205" o el rojo escarlata "196").  
  - Renderizado Simulado: En lugar de dibujar una matriz de caracteres, se utilizarán listas nativas del sistema móvil (como un ListView en Flutter) que simularán el flujo de una terminal mediante animaciones de desvanecimiento ascendente, garantizando soporte nativo para el teclado virtual del teléfono, copiar/pegar y desplazamiento táctil fluido.
  
4. ConclusiónEl proceso de llevar Rizoma a dispositivos móviles requiere abandonar el modelo de un único binario autosuficiente para adoptar un modelo cliente-librería. El núcleo de P2P, criptografía y transferencia de archivos escrito en Go permanecerá intacto y se compilará como un motor subyacente. La red Tor será orquestada por herramientas nativas de cada sistema operativo, y la interfaz gráfica de consola será reemplazada por una aplicación móvil moderna que emulará estéticamente la experiencia de una terminal, logrando así viabilidad técnica y una experiencia de usuario óptima.
